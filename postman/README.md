# Postman

This directory provides the repository-owned Postman artifacts for VellumHub without
turning Postman into a second API specification.

The source of truth remains the OpenAPI document generated by each domain service.
The gateway introduced by issue #165 exposes those contracts through stable
`/docs/{service}/v3/api-docs` routes. `generate.py` reads those live contracts and
regenerates the per-service Postman requests.

Only cross-service sequences are maintained manually because an isolated OpenAPI
operation cannot describe orchestration between multiple requests.

## Files

| File | Purpose |
|---|---|
| `VellumHub.postman_collection.json` | Versioned collection generated from the current live OpenAPI contracts plus the manual cross-service workflow folder. |
| `VellumHub.local.postman_environment.json` | Local environment template. Credentials and tokens are deliberately empty. |
| `workflows.json` | Manually maintained multi-request flows included by the generator. |
| `generate.py` | Standard-library-only OpenAPI -> Postman v2.1 generator. |

## Import and local setup

1. Start VellumHub from the repository root:

   ```bash
   docker compose up -d --build
   ```

2. In Postman, import:

   - `postman/VellumHub.postman_collection.json`
   - `postman/VellumHub.local.postman_environment.json`

3. Select **VellumHub Local (template)**.
4. Set `email` and `password` locally. Do not commit an exported environment containing
   those values.
5. Run **Cross-service workflows**.

The default runner sequence is intentionally read-only and repeatable:

```text
User Service login
  -> Catalog Service list books
  -> Engagement Service current-user ratings
  -> Recommendation Service recommendations
```

The login request stores the returned JWT in `token`, so protected requests do not
require repeated manual token edits. The catalog request also captures the first
available `bookId` for optional examples.

`05 - Optional: rate captured book` is not part of the automatic runner sequence
because it mutates state and may conflict when the same user has already rated that
book.

## Regenerating after API changes

Start the local stack, then run:

```bash
python postman/generate.py
```

The generator fetches these live contracts through the gateway:

| Service | OpenAPI input | Public API prefix |
|---|---|---|
| User | `/docs/user/v3/api-docs` | `/api/v1` |
| Catalog | `/docs/catalog/v3/api-docs` | `/api/v1/catalog` |
| Engagement | `/docs/engagement/v3/api-docs` | `/api/v1/engagement` |
| Recommendation | `/docs/recommendation/v3/api-docs` | `/api/v1` |

The public prefixes mirror `gateway-service/src/main/resources/application.yml`.
Service-local paths still come exclusively from OpenAPI.

Generation fails when a contract is unavailable, is not valid JSON, is not OpenAPI
3.x, has a broken local `$ref`, or contains no operations. This is deliberate: a
partial collection should not silently replace the committed one.

To verify that the committed collection is current without rewriting it:

```bash
python postman/generate.py --check
```

`--check` performs the same live-contract generation and exits non-zero when the
generated output differs from the committed collection.

If the gateway runs elsewhere:

```bash
python postman/generate.py --gateway-url http://localhost:18080
```

## What the generator imports

For every OpenAPI operation, the generator:

- groups requests by service and first OpenAPI tag;
- maps service-local paths to their public gateway prefix;
- carries path and query parameters into the Postman URL;
- creates request-body examples from OpenAPI examples/defaults/schemas;
- supports JSON, multipart form data, URL-encoded forms, and text bodies;
- inherits collection-level Bearer authentication for protected operations;
- explicitly disables authentication for operations whose OpenAPI security is empty;
- derives path-variable placeholders and collection variables deterministically.

This keeps endpoint additions, removals, request schemas, and authentication metadata
driven by the contracts rather than by a manually duplicated route list.

## Manual workflow policy

`workflows.json` is intentionally the only manually maintained request sequence. Add
something there only when its value comes from orchestration, state capture, or a
multi-service scenario that OpenAPI cannot express.

Do not manually copy ordinary CRUD endpoints into the workflow file. Add or improve
the corresponding OpenAPI contract and regenerate instead.

## Secrets and local data

The committed environment contains no real credentials or tokens:

- `password` is empty and typed as a secret;
- `token` is empty and typed as a secret;
- IDs are empty placeholders;
- only `gatewayUrl` and harmless example values have defaults.

Before committing any exported Postman file, inspect it for credentials, JWTs, API
keys, cookies, and Postman current values. Prefer editing the repository template
rather than committing a personal Postman export.

## Validation

The `Postman contract validation` GitHub Actions workflow is intentionally read-only.
It never regenerates files directly on a PR branch or pushes commits.

Static validation:

- compiles `generate.py`;
- parses the collection, environment, and workflow JSON files;
- verifies that committed `password` and `token` values are empty;
- rejects JWT-like values in versioned Postman artifacts.

Live contract validation starts the Docker Compose stack, waits for the four OpenAPI
documents exposed by the gateway, regenerates the complete collection into a temporary
file, and fails if that result differs from the committed collection.

The live drift check is triggered by changes to Postman artifacts and by changes that
can affect HTTP contracts, including service application sources, relevant service
POMs, Docker Compose inputs, and gateway route configuration. This makes the OpenAPI
contracts the enforceable source of truth rather than relying only on contributors to
remember to regenerate manually.

Postman is an exploration and workflow tool here. It does not replace service tests,
distributed integration tests, or the service-owned OpenAPI contracts.
