# Catalog Redis read cache — implementation, operation and evidence

**Scope (merged):** [issue #366](https://github.com/Luca5Eckert/VellumHub/issues/366), [PR #369](https://github.com/Luca5Eckert/VellumHub/pull/369) and [hardening PR #370](https://github.com/Luca5Eckert/VellumHub/pull/370). [C4 Catalog components](architecture/diagrams/c4-catalog-components.md) · [cache sequence](architecture/flows/catalog-cache.md) · [rollout states](architecture/states/cache-rollout.md). The cache accelerates authorized `GET /books/{id}` and `GET /books?pageNumber=&pageSize=` without modifying HTTP DTOs, Catalog ownership, Book Outbox, Kafka contracts or book-cover binaries.

## Architecture and correctness

- `BookReadCache` caches immutable response DTOs using JSON. Book reads use an implicit initial generation until a committed mutation creates a random per-book token with 24h retention; pages share a global generation token created on mutation with no TTL. Redis is configured **noeviction**, volatile/no persistence for local development. In-memory PostgreSQL query state is never used as an authority.
- Cache writes over **128 KiB of UTF-8 JSON** are skipped, recorded as `oversized` and still served from PostgreSQL. Reads of arbitrary/unknown book UUIDs **never create Redis generation keys**; absent generations use a constant initial epoch, and only an after-commit mutation creates a random per-book marker (24h, greater than all response TTLs). This prevents a flood of authenticated 404 lookups from exhausting noeviction memory. Cache keys are versioned (`vellumhub:catalog:response:v1:`) and include book UUID or `pageNumber/pageSize` and `createdAt-id` sort version, plus generation. A read started before an update can only fill its old generation key; it cannot repopulate the new key after a successful invalidation.
- `OutboxBookChangeWriter.record` is the single mutation boundary; after an outbox append, the cache registers an **afterCommit** invalidation. This covers create, ISBN import, update, delete/soft-delete, approval of a Book request and both cover metadata paths. A no-op update without an outbox fact does not invalidate; rollback does not call afterCommit.
- Book detail invalidation affects only the changed ID; every Book change bumps the page generation, since inserting/deleting/changing metadata can shift any page. Invalidation failure cannot roll back an already-committed DB write. **Residual stale responses are bounded by TTL**, not a linearizable guarantee. If a reader was already started, its response can reflect the previous snapshot.
- Cache hit authorization is enforced by the existing Catalog `SecurityFilterChain` with OAuth2 JWT/scopes *before* entering `BookController`; no JWT, user ID, ISBN or book ID is exported into metric labels. No negative/404 or empty page caching.
- Single-flight coalesces same-key misses *within one JVM* (256 concurrent in-flight keys, 5s follower timeout). A follower reaching that deadline gets a deliberate HTTP **503 + Retry-After: 1** instead of initiating another PostgreSQL request. A fair 64-permit JDBC bulkhead, with a 500ms admission budget, also caps cache misses, Redis-outage fallbacks and in-flight-capacity overflow. Requests exceeding this threshold fail fast and are counted as `db-rejected`. The read-OFF path remains the ordinary PostgreSQL path. Across pods, each replica may have one leader; this is deliberately not a distributed mutex.
- Redis errors and corrupt cached JSON fall back to PostgreSQL, subject to the same DB concurrency bulkhead when reads are ON. Redis is excluded from liveness/readiness. If memory reaches `maxmemory`, new writes can fail without breaking reads, but hit rate degrades; monitor it.
- Pagination is normalized by `PageBook` before lookup and JPA now sorts by `createdAt ASC, id ASC`. Hibernate `@BatchSize(50)` reduces lazy genre N+1, and Flyway V6 provides indexes for visible-book paging and the genre FK. These SQL fixes are independent of Redis.

## Supported configuration and activation

| Setting | Default application property | Local Compose / Kind |
| --- | --- | --- |
| `CATALOG_CACHE_ENABLED` | `false` | `true` |
| `CATALOG_CACHE_INVALIDATION_ENABLED` | Inherits the read flag; default `false` | `true` |
| `CATALOG_CACHE_REDIS_HOST` | `localhost` | `redis-recommendation-cache` |
| `CATALOG_CACHE_REDIS_PORT` | `6379` | `6379` |
| `CATALOG_CACHE_DETAIL_TTL_SECONDS` | `300` | `300` |
| `CATALOG_CACHE_PAGE_TTL_SECONDS` | `45` | `45` |
| `RECOMMENDATION_CACHE_ENABLED` | `false` | `true` |
| `RECOMMENDATION_CACHE_TTL_SECONDS` | `45` | `45` |

Local domain caches share the **cache-only** Redis named `redis-recommendation-cache` for backward compatibility. The Gateway rate limiter uses a separate Redis service. Namespaces, TTLs and generations remain independently managed. Consider renaming the service when operations standardize a domain-wide cache cluster; no separate Redis per service is needed at this stage.

**Two-phase rollout is mandatory for Catalog and for any mixed-version fleet.** Read-cache activation and writer invalidation are independent so a temporary read-OFF instance can still invalidate data cached by other pods. **Phase A:** deploy a version with `CATALOG_CACHE_INVALIDATION_ENABLED=true` to **all** Catalog writers, while `CATALOG_CACHE_ENABLED=false` everywhere; verify that no old binaries that skip invalidation are still serving writes. **Phase B:** enable `CATALOG_CACHE_ENABLED=true` gradually and monitor HIT, staleness and DB capacity. A cache reader configured true while invalidation is false fails startup. **Rollback:** first turn read caching OFF on every pod, then (only if necessary) disable invalidation. Never reverse that order, and never mix old PR #369 binaries (which skip invalidation when read OFF) with any cache-reading pod. In a failure or forced old-binary rollback, disable **all** readers and allow up to the maximum detail TTL to elapse before re-enabling. This limitation cannot be removed by a JVM-local flag.

**Production overlay is intentionally OFF** for both caches. It still contains a placeholder external Redis host and lacks proof of managed endpoint, TLS/ACLs, memory budget, traffic reuse or measured rollback. Turning it ON by changing a YAML boolean would not provision or deploy a production Redis. Do not describe the GitHub merge, Kind tests or this local toggle as production activation. A production rollout must provision an isolated managed Redis endpoint, secrets/ACL, noeviction policy suitable for generation keys, network policy, memory budget and a verified canary rollout.

Rollback: set `CATALOG_CACHE_ENABLED=false` or `RECOMMENDATION_CACHE_ENABLED=false` and redeploy that service. The original JPA/pgvector read path remains functional; no Redis key flush, SQL down migration, JVM process restart beyond redeploy, or schema migration rollback is required. PostgreSQL is the authority.

## Measurements and CI

- `BookReadCacheTest`: bypass, Redis outage, failure propagation.
- `BookReadCacheNoEvictionIT`: disposable 1.8 MiB Redis with noeviction, enough distinct real-size Catalog pages to trigger OOM command rejections; PostgreSQL-backed reads stay successful.
- `BookReadCacheLoadSheddingTest`: 80 concurrent Redis-offline misses, maximum 64 DB loads, explicit bounded rejections.
- `BookReadCacheRedisIT`: real Redis with independent clients, detail/page HIT, arbitrary 404 ID markers absent, delayed leader, two-phase read-OFF/invalidation-ON writer, TTL expiry, cleared Redis restart simulation, fallback on refused Redis TCP and bounded single-flight. This is one JVM, not two application processes.
- `CatalogCacheTwoContextsIT`: two separately bootstrapped Spring Boot Catalog contexts against the same PostgreSQL/Redis, authenticated MockMvc in both, committed writer update/delete through actual BookService/Outbox and rollback of a real transaction; tests an active reader and read-OFF/invalidation-ON writer. It is not a multi-process/network-TLS benchmark.
- `CatalogCacheRedisOutageBootIT`: the full Spring Boot Catalog context starts while Redis TCP port refuses connections; authenticated HTTP read and committed write still use PostgreSQL.
- `CatalogCacheNetworkHttpIT`: real TCP HTTP to a RANDOM_PORT Spring Boot server with a locally generated **RS256-signed access JWT**, a local JWKS server, 401 without token / 403 without scope, warm HIT payload equality, and Book update/delete freshness after commit; all with real PostgreSQL/Redis Testcontainers. This is a functional HTTP/network test, not the A/B load benchmark.
- `CatalogCacheReadBenchmarkIT`: authenticated MockMvc with real PostgreSQL/JPA/Flyway + Redis Testcontainers. Tests detail IDs and stable paginated reads, four modes `cold/warm/mixed80/mixed95`, three client concurrencies and repetitions, latency p50/p95/p99, throughput, PostgreSQL/Hibernate prepared-statement count, response hash/equivalence OFF/ON, worker-thread CPU, heap usage/delta, GC, sampled Hikari connections, Redis keyspace hits/misses and memory, SQL EXPLAIN ANALYZE/BUFFERS, HTTP errors; raw JSON `on.json`/`off.json` with same commit, code, seed and runner category.
- [Catalog Redis cache benchmark workflow](../.github/workflows/catalog-cache-benchmark.yml) executes OFF and ON in separate JVM/Maven runs, and uploads JSON/JUnit evidence. It uses `reference` (1,000 requests per scenario x 3 repetitions x concurrency 1/8/32; **72k requests OFF+ON**) for the reference PR workflow (including #370); `smoke` is 120 requests per scenario / 1 repetition / concurrency 1/8. A manual `stress` profile is 3,000 requests per scenario x 3 reps x concurrency 8/32/64 (216k OFF+ON).
- No threshold based on absolute CI runner latency is used; successful responses and warm-cache zero JPA prepared statements are correctness assertions. **Only report measured results after the workflow succeeds and the raw artifacts are inspected**. An earlier 72k benchmark of Recommendation PR #367 does not measure Catalog performance.

The [PR #370 benchmark](https://github.com/Luca5Eckert/VellumHub/actions/runs/43666479401) passed with 72,000 authenticated OFF/ON requests, identical response digests, 2,200 books with two genres each, SQL plans and resource metrics. Warm/c32 p95 improved 44.89→10.35 ms; cold/c8 regressed 8.10→13.41 ms. The benchmark drives MockMvc within one process, **not network HTTP throughput**, and cannot establish p95, Redis RTT or memory behavior in a remote production cluster. A real GO for production requires workload-specific hit ratio and access-key distribution, p95/p99 under HTTP/TLS, CPU/GC/pool/memory/evictions, Redis outage/canary recovery and freshness after writes, plus rollback evidence.

## Observability

Micrometer `vellumhub.catalog.cache.events{cache="books",result="hit|miss|bypass|error|corrupt|leader|waiting|joined|capacity|timeout|interrupted|invalidate|invalidate-error|db-rejected|oversized"}` and `vellumhub.catalog.cache.serving.duration` are available on the existing Prometheus actuator endpoint. Denominators should exclude bypasses when interpreting hit ratio. No book IDs or customer identifiers in labels. Monitor Redis `used_memory`, noeviction write failures and remaining TTL separately from JVM metrics.

Source files: `module/book/infrastructure/cache/BookReadCache.java`, `module/book/application/event/OutboxBookChangeWriter.java`, `module/book/application/handler/get/GetAllBooksHandler.java`, Flyway `V6__index_visible_book_page_and_genres.sql`.

## PostgreSQL index migration on populated databases

Flyway V6 remains **immutable** after it has been applied. Its `CREATE INDEX IF NOT EXISTS` statements are transactional and can block writers on large tables. Before the first startup that applies V6 on a populated environment, run `tools/sql/catalog_cache_preflight_indexes.sql` with `psql -v ON_ERROR_STOP=1 -f ...` **outside any transaction**. It creates the same two indexes with `CONCURRENTLY IF NOT EXISTS`, after which Flyway V6 can validate its unchanged checksums and observe both index names already present. Validate `pg_index.indisvalid` and analyze the real `EXPLAIN (ANALYZE, BUFFERS)` for `books(deleted_at,created_at,id)` and `book_genre_id(book_id)` before enabling cache traffic. If V6 was already applied, do not edit or rerun it; use a separately reviewed corrective migration when necessary.

## Operational limitations and explicit non-goals

The 128MiB cache-only Redis in Compose/Kind remains a **local fixture**, not a production capacity plan. Its `noeviction` policy is intentional so eviction does not independently discard generation markers; `maxmemory` writes can fail, with read-through continuing at the DB. Monitor `db-rejected`, `oversized`, Redis memory, keyspace hit rate and PostgreSQL connection saturation. No deployment or canary is performed by GitHub Actions. External HTTP/TLS latency and Redis/Kafka failure injection in a production-like multi-pod cluster require an environment-specific gate; two Spring contexts in one test process are not a substitute.
